> **配套文档**：规格在 `docs/rag-任务书.md`（每个任务做什么、验收标准），本文只管**顺序、门禁、风险**，不重复规格。
> 家底与坑在 `docs/rag-现状盘点.md`。
>
> **一句话原则**：先离线拿数字，数字不成立就不接入产品。

---

## 一、三条不可动摇的原则

1. **先离线后在线。** 任务 A + B 全部离线可验证、可重跑、成本极低。C（接入产品）以 B 的数字为**前置条件**，不是后续步骤。
2. **每个阶段有决策门，门不过就停。** 不做「先接着往下写，回头再调」——RAG 的失败是静默的，越往后堆越难定位。
3. **最耗时的不是代码，是人工标注。** 评测集 30~40 条要逐条核对答案片段，这是 P3 的真实瓶颈。排期时把它当独立工作项，别当成写代码的副产品。

**过程中发现并修掉的两个真实 bug**（都是真实语料才暴露出来的，构造文本测不到）：

1. **未闭合围栏导致巨块**。语料里有被采集侧截断的 README，围栏没闭合时 `_fence_ranges` 会把围栏尾巴伸到文末，避让逻辑于是把切点一路推到文末，切出过 **22,385 字**的巨块（上限的 11 倍）。修法：给「推到围栏之后」加一个 1.5 倍上限，超了就在围栏内部切 —— 切坏一段代码，好过产出一个上万元的巨块。
2. **零长度块与纯分隔符块**。围栏避让恰好把切点推到段尾时会多补一个空段；两个标题紧挨着时会产生只有 `"\n\n---\n\n"` 的块。前者会向量化成一个无意义的点，后者在检索结果里白占名额。修法：段尾不再补空段；新增「无内容」判定，这类块无条件并进相邻块（**不能只靠 `min_chars`** —— 它的合并有容量上限，前一块接近上限时这类块就漏网了）。

> 这两条本身就是最有说服力的工程证据：它们证明这套切分在真实语料上跑过，而不是只靠构造测试。

**踩了两次的坑：token 估算的两轮修正**

第一轮（小样本时发现）：最初按「中文 0.65 / 其他 0.286 token/字符」估，实测**低估 11%**。

第二轮（全量时暴露，更严重）：**估算只区分了「中文 / 其他」两类，而韩文被算进了「其他」。**
韩文实测是 **1.24~1.63 token/字符**，被按 0.286 估，低估 4~6 倍。后果：

- 估算说 648 token，实际 2000+，请求被 400 拒绝，错误信息是 `Range of input length should be [1, 2048]`
- 而这是**批量请求** —— 25 条里有一条超限，**整批 25 条一起失败**
- 于是两张卡（`gh-1350986681` 60 块、`gh-1354310030` 28 块）**永远写不进去**，
  报错只显示「25/60 块向量化失败」，看不出根因。重跑三次都卡在同一处

修正过程本身也踩了一次：先按 500 字符的均匀韩文样本测出 1.24，取系数 1.40 —— **仍然偏低**，
真实混排块（1,094 韩文 + 890 拉丁/符号）实测 1.63，请求照样被拒。

**最终结论：token 密度不是文本的固有属性，它依赖上下文。** 均匀样本测出的密度只能当参考，
系数必须往上取（最终韩文取 1.75）；而且**光靠估算不足以保底** —— 所以对「估算已超预算」的
极少数块（0.007%），加了真实的**逐块降级**：整批失败 → 逐条重发 → 按 `SHRINK_LADDER`
（0.85/0.70/0.55/0.40/0.25）截断再发。把不确定的估算换成确定的验证。

> 这条是**最有说服力的工程证据**，因为它比「实现了 RAG」具体得多：一个只在真实语料
> （韩文 README）+ 真实协议（批量请求整批失败）交叉处才出现的 bug，以及两轮都没修对、
> 第三轮才定位到「估算的粒度本身不够」的过程。

### P3 · 检索 + 评测（**分水岭**）

**做什么**
1. `retriever.py`（复用 `QDRANT_READ` 熔断 + `clamp_timeout`）。
2. **人工标注评测集 ≥ 30 条**，标签锚定**原文字符区间**，按 `lang_pair` 分三组。
3. 跑出**四张表**：切分策略 / 重叠 / 纯向量vs混合 / 按 difficulty。

**产出**：`retrieval_runner.py` + `retrieval_cases.json` + `retrieval_<ts>.md` + `retrieval_baseline.json`。

**门（主门禁）**：**「按标题切」的命中率显著高于「固定长度」**。

- 若成立 → 拿到 `02-rag.md` §Q5 追问的答案，**可以进 P4**。
- 若**不成立**（差异在噪声内）→ **不要进 P4**。按下面顺序排查，每步都要重跑表：

```
命中率不理想
 ├─ 第 1 步：先看 lang_pair 分组
 │    若 zh_query_en_doc 明显低于 en_query_en_doc
 │    → 是跨语言问题，不是切分问题
 │    → 换中文优化的 embedding（阿里云 Qwen）重算块向量，再跑
 ├─ 第 2 步：看混合检索有没有收益
 │    若 hybrid >> vector，说明向量那一路在英文原文上确实弱
 │    → 保留 hybrid 作为主路径，把它写进结论
 └─ 第 3 步：看 difficulty 分组
      若 detail 明显低于 overview → 块太大，主题被平均
      → 调小 max_chars 重跑
```

**关键纪律：先修检索，再修提示词。** 顺序反了会在注定修不好的事情上耗掉大量时间，而且改完「感觉好了一点」—— 提示词改动本来就伴随随机波动。

**六个设计决定（都是「做错了不报错」的类型）**

1. **查询侧传 `text_type="query"`** —— 非对称检索。传成 `"document"` 不报错，只让排序悄悄变差。
2. **熔断检查放在 embedding 之前** —— Qdrant 已连续失败时先算查询向量是白花钱（embedding 按量计费）。顺序反了不报错，只是熔断期间每个请求都多付一次费用。
3. **阈值后置过滤，不用 Qdrant 的 `score_threshold`** —— 服务端过滤会丢掉「最高分是多少」，而「库里没有」和「有但不够像」的处置完全不同（补语料 vs 调阈值）。
4. **Qdrant 调用整体丢线程池**，含 `get_chunk_store()` 本身（构造期有一次 `get_collections()` 往返）。顺带把 `get_chunk_store` 补进了 AST 守卫的工厂名单。
5. **正文回填要防「索引后原文被改过」** —— 偏移量越界时**拒绝截断凑合**，那会得到一段看起来正常但实际错位的文字。残余风险（长度没变但内容换了）需要 payload 存块正文哈希，列为后续项。
6. **空结果也要报最高分** —— 否则「没资料」和「不够像」在观测上分不开。

本集是 **agent-grounded**：问题由标注者**读真实原文后**按具体段落写出，答案区间由脚本
在 `raw_content` 里**唯一定位**（找不到或出现多次直接报错）。它**不是独立第三方人工标注**
—— 所以命中率是**乐观上界**。它的可信之处是**策略之间的相对高低**，不是绝对水平。

> 为什么不是「人工标注」也能用：**评测的目的决定了标注的要求**。这里要回答的是
> 「按标题切比固定长度好吗」这类**相对**问题，不是「上线后用户满意吗」。
> 相对问题只要两套策略用**同一套标签**，出题者的用词偏好就被抵消了。
> 但绝对水平必须打折看 —— 报告里每次都带这句。

| 语种对 | n | hit@1 | hit@5 | hit@10 | MRR |

**三条结论**

1. **跨语言是明确的短板**：zh→en 的 hit@1 只有 27.3%，不到 zh→zh（58.3%）的一半。
   这**正好命中 P0 语料体检预警的那条风险**（原文 77% 是英文、摘要 95% 是中文）。
   下一步的候选对策有明确优先级：换 Qwen embedding 重算 → 中文摘要做锚 → 混合检索。
2. **hit@5 (77.8%) 与 hit@10 (88.9%) 差 11 个点** —— 说明**答案大多已经召回到了，
   只是排序不够靠前**。这是「该上重排」的直接证据，而不是「该换模型」。
   **没有这张表，重排就是个凭感觉的决定。**
3. **阈值 0.35 是稳的**：10 条语料外问题一条都没漏进来，最高分 0.2840 距阈值还有 0.066。
   所以「拒答」这一环暂时不用动，**该动的钱花在召回排序上**。

**口径纪律（两条）**

- **排序指标不过阈值**（`min_score=0.0`），**拒答指标才过阈值**。混在一起会出现
  「阈值调高 → 命中率下降 → 看起来检索变差」的假象，其实只是砍得更狠。
- **判定用「包含」不用「重叠」**：重叠会把「答案跨在两块交界、各拿一半」也算命中，
  而那种情况模型拿到的信息是残缺的。严口径是 `hit@k` 数字偏低但**能信**的原因。

> ⚠️ **当前状态的口径（已更新）**：检索**链路**通了、**命中率**也有了
> （hit@5 **77.8%**，且**这是乐观上界**）。
> 对外可以说明「我标了 46 条评测集、hit@5 77.8%、跨语言是短板」，
> 但要**同时说出「标签是我自己按原文出的，所以偏乐观」** —— 不说这句，数字就站不住。

## 四、风险与止损线

| # | 风险 | 概率 | 对策 |
|---|---|---|---|
| 1 | **跨语言导致命中率低** | 高 | 已识别（原文 77.2% 英文 / 摘要 94.7% 中文）。对策顺序：换 Qwen embedding 重算 → 混合检索 → 中文摘要做锚。**不要一上来就怀疑切分。** |
| 2 | **标注集质量差** | 中 | `answer_span` 必须用脚本校验「在原文中存在且唯一」；抽样避开被截断的尾部。 |
| 3 | **成本失控** | 低 | P2 小样本先实测单价再放大；全量前给用户确认。 |
| 4 | **换 embedding 模型后忘记重算** | 中 | 块 payload 必带 `embedding_fingerprint`；入库脚本提供 `--rechunk`。 |
| 5 | **评测集被自己调成「好看」** | 中 | 调了就要在报告里写明调之前是多少、为什么调。**低命中率 + 正确归因，比高命中率更抗追问。** |

### 止损线（重要）

**如果 P3 做完四张表仍然没有区分度**（各策略命中率都在噪声里、混合检索也无收益）：

**不要做 P4 / P5，直接跳到 P6。**

理由：这时的正确产出不是「一个接入产品的半成品」，而是**一份有数据的失败诊断** —— 它同样是这条链路的价值证据，而且比成功故事更难被追问穿：

> 「我把检索链路做完了，四张表都跑了。结论是我的语料不适合做细粒度检索 —— 原文 77% 是英文，中文提问命中的是跨语言相似度而不是真实相关。我做了混合检索，收益有限，因为我意识到问题在**语料语言分布**，不在切分参数。所以我停在了检索层，没有接入产品 —— 接入只会把问题藏起来。」

这段话的价值**高于**「我做了 RAG，命中率 90%」。因为后者必然被追问「你的评测集怎么标的」，而前者展示的是判断力。

## 五、相对任务书的一处技术修正

**混合检索的关键词那一路，用 `pg_trgm`，不要用 `to_tsvector`。**

实测（PostgreSQL 18.6）：

| 项 | 结果 |
|---|---|
| `zhparser` / `pg_jieba` | **均不可用**（`pg_available_extensions` 里没有） |
| `default_text_search_config` | `pg_catalog.simple` |
| `pg_trgm` | **可用** |

`to_tsvector('simple', 中文)` 会把整段中文当成一个 token（按空格切），中文检索**完全失效**。而 `pg_trgm` 基于字符三元组，**不依赖分词**，中英文都能用，对英文专有名词（`Qdrant` / `dimension` / `API`）效果尤其好 —— 这正是技术提问里最关键的检索词。

→ 实现：`pg_trgm` 的 GIN 索引 + `similarity()` 排序。需 `CREATE EXTENSION pg_trgm`（走 Alembic 迁移，保证可 downgrade）。
