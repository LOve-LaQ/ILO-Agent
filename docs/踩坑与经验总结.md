## 1. 环境与基础设施类（E）

环境类问题是最磨人、最容易被误判的一类：**报错现象和真实原因往往完全不相干**。

### E1. Windows 中文路径导致模块导入失败

- **现象**：Python 脚本报 `Could not import module 'C'`。
- **根因**：路径含中文字符时，`subprocess.run()` 把完整文件路径当成模块名传给 uvicorn。
- **解决**：改用模块路径方式启动 —— `uvicorn src.api.main:app --reload`，而不是 `python C:\Users\ZY\...\main.py`。
- **教训**：在 Windows + 中文用户名环境下，任何「把路径当模块名」的调用都可能踩雷。

### E2. Windows 下 `localhost` 解析成 IPv6 导致容器连不上

- **现象**：Docker 容器里 Qdrant/Redis 服务正常，后端却拿 502 / 连接被拒绝。
- **根因**：Windows 把 `localhost` **优先解析成 IPv6 `::1`**，而 Docker 容器只监听 IPv4 → `[WinError 10054]`，把「服务正常」误报成「服务未启动」。
- **解决**：所有服务地址从 `localhost` 改为 `127.0.0.1`。涉及 `.env`、`.env.example`、`config.py`、`tech_knowledge.py`、`memory_manager.py`、`discover.py`、`learning.py`、前端。
- **教训**：Windows 上排查容器连通性，**第一条就换成 `127.0.0.1`**。区分报错码：`10054` = 端口被转发代理占着（先接受再重置），`10061` = 端口无人监听。

### E3. Qdrant 容器退出导致首页只剩 3 条示例卡片

- **现象**：首页推荐流恒定只显示 **3 条**卡片，登录与否一样；日志出现 `[WinError 10054]` 与 `知识库不可用`。
- **根因（两层）**：
  1. Qdrant 容器 `ilo-agent-qdrant` 被停止 —— `RestartPolicy=no`、无崩溃栈、`OOMKilled=false`，即 Docker Desktop / WSL 关闭时被强制终止且不自恢复，**每次开机后它都是停的**；
  2. 容器一停，`GET /api/v1/discover/news` 的三级降级链（知识库 → Redis 缓存 → `FALLBACK_NEWS`）落到兜底数组，而该数组**只有 3 条示例**，故 `limit=6` 也只能返回 3 条。
- **解决**：`docker start ilo-agent-qdrant`，`curl http://127.0.0.1:6333/healthz` 返回 200 验证。根治：给 compose 服务加 `restart: unless-stopped`，并对**已存在**容器补 `docker update --restart unless-stopped <容器名>`（只改 compose 文件对已建容器不生效）。
- **教训**：**带降级兜底的接口，数据量少会伪装成「页面数据缺失」而非报错**。排查时先看日志里的上游警告 + 核对容器状态，不要先怀疑前端渲染或权限过滤。

### E4. Docker healthcheck 用了镜像里不存在的命令

- **现象**：容器长期 `unhealthy`，但服务实际可用（Qdrant 正常响应 6333）。
- **根因**：healthcheck 写成 `["CMD","curl","-f","http://localhost:6333/status"]`，而 qdrant 镜像（Debian 系）**没装 curl/wget**，检测命令自身失败即被判不健康。
- **解决**：先 `docker exec <容器> command -v curl wget bash` 确认有什么，再选探针。本例只有 bash，改用 `/dev/tcp` 探端口：`["CMD-SHELL","bash -c 'echo > /dev/tcp/127.0.0.1/6333'"]`。改动后需 `docker compose up -d --force-recreate <服务>` 才生效。
- **教训**：写 healthcheck 前**先确认命令在镜像内存在**。

### E5. `alembic.ini` 被按 GBK 读取

- **现象**：Alembic 读取配置报 `UnicodeDecodeError`。
- **根因**：Alembic 以 `encoding="locale"` 读取 `alembic.ini`，而中文 Windows 的 locale 是 GBK。
- **解决**：该文件**必须保持纯 ASCII 注释**。
- **教训**：跨平台工具链的配置文件，**不要写非 ASCII 字符**。

### E6. Docker 拉取镜像网络失败

- **现象**：`docker pull`/`docker run` 报 `dial tcp <IP>:443 ... did not properly respond`。
- **根因**：中国大陆无法直连 Docker Hub（`registry-1.docker.io`）。
- **解决**：① 配置镜像加速器（`%APPDATA%\Docker\config\daemon.json` 的 `registry-mirrors`）；② 设置 `HTTP_PROXY`/`HTTPS_PROXY`；③ 离线方案下载单机版二进制。
- **教训**：网络问题优先怀疑链路而非配置。

### E7. feedparser 在 Python 3.13 挂掉

- **现象**：RSS 抓取引擎无法导入。
- **根因**：feedparser 的 `encodings.py` 仍 `import cgi`，而 `cgi` 自 Python 3.13 起被移除。
- **解决**：最终**直接删掉零引用的 RSS 引擎**（`engine.py` / `simplified_engine.py`）及 `feedparser` / `lxml` / `beautifulsoup4` 三个孤立依赖（提交 `b5b0394`）。
- **教训**：**依赖与被依赖代码必须一起删**。这一步是「证明零引用后再删」的标准流程。

## 2. 后端架构与代码类（B）

### B1. 顶层导入重型依赖拖慢启动

- **现象**：首个请求（`/auth`、`/discover`）要等十几秒，前端顶栏长时间空白，但单个接口本身很快。
- **根因**：路由模块顶层 `from src.modules.agent import ...` 连带导入 langchain / transformers / torch。实测 `import src.api.main` 达 **9.14s**，其中 `src.modules.agent` 占 **8.04s**（torch ≈2.4s、transformers ≈3.1s），而启动路径并不需要它。
- **解决**：把导入从模块顶层**下沉到真正使用它的函数体内**（如 `learning.py` 的 `get_state_machine()`），保留懒加载单例（提交 `7e331ba`）。
- **代价**：首次调用该接口会多一次导入（8.32s）。
- **教训**：排查启动慢先做**导入剖析**，把「只有部分接口才需要的重依赖」移出顶层。

### B2. 同一文件在同一消息里并行编辑会互相覆盖

- **现象**：8 个 Edit 只落盘 3 个，但工具仍报 `Successfully edited`。
- **根因**：同消息内对同一文件并发编辑，后写覆盖先写。
- **解决**：同文件**必须串行编辑**，或改用「带断言的批量替换脚本」（原子性：任一断言失败则一个字节都不写）。
- **教训**：工具报 Success ≠ 全部生效。**改同文件的多次编辑不能并行。**

### B3. 模块级常量插到类体里导致 `IndentationError`

- **现象**：插入常量后语法报错。
- **根因**：把模块级常量插在了**类方法**作锚点的位置，常量落进了类体。
- **解决**：模块级常量必须插在**模块级锚点**（如 `COLLECTION = ...`）附近。
- **教训**：用锚点定位插入时，要保证锚点的**缩进层级**与目标一致。

### B4. SQLAlchemy 漏 commit 导致写入静默回滚

- **现象**：写操作「报告成功但数据没落库」，且不报错、不易察觉。
- **根因**：`with get_session_factory()() as session:` 退出时**只 close 不 commit**，事务被回滚。若同一次调用用了 `pg_insert(...).on_conflict_do_nothing(...).returning(...)`，`RETURNING` **仍会返回新行主键** → 函数返回「已新建」，调用方与用例全被骗过；重复调用还会永远返回 `changed=true`。
- **解决**：凡是写操作，必须在 `with` 块内**显式 `session.commit()`** 后再返回结果（读操作不需要）；判定「是否新建」的布尔值要**先取出、再 commit、最后 return**。
- **教训**：当写接口的失败被 `try/except` 静默吞掉时，漏 commit **不报错也不告警**，只有**落库后回读**（或端到端验证）才能发现 —— 写路径必须有「写完再读」的断言。

### B5. 导入前缀不统一导致同一文件被加载两次

- **现象**：全局异常处理器失配，`ILOException` 身份不一致。
- **根因**：混用 `core.` 与 `src.core.` 导入前缀，会把**同一个文件加载成两个模块**（两份类对象）。
- **解决**：后端导入前缀**统一为 `src.`**。
- **教训**：Python 中「模块身份」由导入路径字符串决定，前缀混用是隐蔽的深坑。

### B6. pytest 假用户该防落库却污染了开发库

- **现象**：跑一次全量测试就往**真实开发库**写脏数据，不报错、不易察觉（实测约 29 条流水 + 4 条对话）。
- **根因**：`conftest.py` 用固定假用户 id 覆盖 `get_current_user`，以为「用户不在库 ⇒ 外键失败 ⇒ 不会落库」。但两类漏网：① 外键为 `ondelete="SET NULL"` 的流水表（`user_activities`）；② **完全没有外键**的表（`chat_messages`）。
- **解决**：① 测试指向独立测试库（`TEST_DATABASE_URL`）；② 或 session 级 fixture 统一按前缀回收，并断言「测试结束后无残留」。
- **教训**：**新增「best-effort 落库」后必须同步检查测试隔离** —— 只要表没有外键或是 `SET NULL`，假用户 id 就防不住写入。

### B7. 观测代码反过来炸掉主流程

- **现象**：一次网络故障被伪装成 `AttributeError`。
- **根因**：`timeout_s=self.http_client.timeout.read` —— 客户端被替换成桩（无 `timeout` 属性）时抛 `AttributeError`，把原始下游异常顶掉；`scope=self._current_provider` 同理。
- **解决**：防御式读取 —— `_read_timeout_s()` 读不到返回 0；`getattr(self, "_current_provider", "") or ""`。
- **教训**：**观测字段永远不该反过来炸掉主流程**。

### B8. 「配置接线成功」不等于「调用成功」

- **现象**：见 [A4](#a4-qdrant-按次超时传-float-导致写入必然失败)。
- **根因**：当时做的是「运行时穿透」验证 —— 断言客户端对象上带上了配置值，但真正会炸的是**调用**，不是**构造**。
- **解决**：把验证打到**调用层**（真实发起一次请求）。
- **教训**：**验证必须打到实际执行路径**，构造成功只是必要条件。

## 3. 异步与可靠性类（A）

这一组是项目里**最有价值**的一段：从「发现 P0 缺陷 → 写任务书 → 修复 → 量化验证」的完整闭环（任务书见 `docs/tasks/timeout-and-resilience.md`）。

### A1. LLM 同步调用阻塞事件循环

- **现象**：一次 LLM 调用（几百 ms 到几秒）**独占事件循环**，期间所有其他请求（含 `/health`）排队，单实例并发一上来就雪崩。
- **根因**：4 个 LLM 调用点里，`learning.py` 的 chat 与 `state_machine.py` 的讲解用了**同步 `llm.invoke()`**（被 async 方法包裹但没卸载）。
- **解决**：`await asyncio.to_thread(llm.invoke, prompt)`，并把 `timeout` 传进被调函数。
- **实测**：50.02s 的 LLM 调用期间，事件循环最大卡顿 **38ms**（修复前 ≈50000ms，**改善约 1300 倍**）。

### A2. 「修 A 引入 B」：`to_thread` 包住协程

- **现象**：响应校验失败（`string_type` 错误）。
- **根因**：讲解原本用 `asyncio.to_thread` 包 `ExplanationEngine.generate`，但那是 **async 协程**，`to_thread` 拿到的是**未 await 的协程对象**。当时改成直接 `await` 修好了校验，**但代价是变成同步阻塞** —— 典型的「为了修 A 引入 B」。
- **解决**：让 `generate` **保持 async**，只把它**内部**的同步 `llm.invoke` 卸载到线程池。任务书里专门加了**防回归要求：不许退回旧方案**。
- **教训**：改异步问题时，「修好一处」要以不引入新阻塞为前提。

### A3. 搜索维度错了：从 2 处变成 80 处

- **现象**：第三方复测发现 `/discover/news` 在 async 路由里同步调了整条 DB + Qdrant 链；全量审计后**同类问题共 80 处**（`discover.py` 19 / `learning.py` 38 / `me.py` 23）。
- **根因**：第一次按「**哪些地方调了 LLM**」去找阻塞，只能找到 LLM；正确维度是「**`async def` 函数体里出现了哪些同步 IO**」。
- **解决**：① 全量清理 80 处；② 加 **AST 静态守卫** `tests/_async_io_guard.py` + `tests/test_async_no_blocking_io.py` 防回归；③ 三个非机械改动（见下）。
- **为什么全量而不只修一处**：因为同时要加守卫。只修一处，守卫会立刻在其余 79 处失败，那时只剩两条路 —— 留一个带 baseline 豁免的**假绿**，或补完。**带 baseline 的守卫等于没有守卫。**
- **三个非机械改动**（简单套 `to_thread` 会引入新 bug）：
  1. **新增 `log_activity_async`**，而不是把 `log_activity` 改成 async —— `auth.py` 是同步路由，改 async 会让它拿到**未 await 的协程**（埋点全丢）；
  2. **三个惰性单例加锁**（`get_knowledge_base` / `get_state_machine` / `get_memory_manager`）—— 挪到线程池后不再天然串行，并发首调会各自构造一次，而 `get_state_machine` 每次构造要付 **8s 的 import**。这是「把同步调用挪到线程」**必然带来的副作用**；
  3. `os.getenv("REDIS_URL"/"QDRANT_URL")` 统一改走 `settings` —— `discover.py` 的 Redis 客户端此前**没配 `socket_timeout`（无限等）**。
- **实测**：下游每次阻塞 500ms、共 2 次 → 请求 1073ms，事件循环最大卡顿 **8.9ms**（对照组 **506.0ms**）。测试 251 → **263 passed**（提交 `9d0f033`）。
- **教训**：**按技术栈维度搜，必然漏掉同类调用**。这个教训比修好的 80 处更值钱。

### A4. Qdrant 按次超时传 float 导致写入必然失败

- **现象**：抓取完前端仓库数不涨，弹绿色「✅ 新增 23 条」，实际 **0 条入库**。
- **根因（两层，缺一不可）**：
  1. **P0 回归**：`qdrant-client` 1.19 的 REST 客户端在 `api_client.py` 做 `int(kwargs["params"]["timeout"])`，而该值进来前**已被序列化成字符串** → `int("6.0")` → `ValueError`。异常发生在**客户端构造请求时**，请求根本发不出去 ⇒ **任何非整数超时 = 这次 Qdrant 调用必然失败**。上一轮加了 3 处按次浮点超时（`upsert` 写档 6.0 / `query_points` 读档 4.0），于是所有向量写入静默失败（异常被 `collect_items` 逐条 `try/except` 吞掉）；
  2. **P1（把失败掩盖了）**：`collect_items` 在整批失败时把批次标为 `failed`，但返回给调用方的 `CollectResult.status` **硬编码 `"ok"`** → 接口回 `status: ok` → 前端弹绿色成功。
- **解决**（提交 `79d6358`）：
  1. 新增 `resilience.py::qdrant_timeout_seconds()`：**向上取整 + 下限 1**（下限 1 是因为 Qdrant 里 `timeout=0` 是「不设超时」，与「预算耗尽」正好相反）；替换 3 处调用点；构造期**刻意不包**并注释说明；
  2. `CollectResult.status` 如实映射 `succeeded→ok / partial→partial / failed→error`；
  3. `RefreshResponse` 增加 `failed_count`，前端按四态提示；
  4. 新增 `tests/test_qdrant_timeout.py`（18 例），含**反向钉住第三方行为**的测试：哪天 qdrant-client 修了 `int(str(x))`，该测试会失败并提醒可删包装；
  5. 顺手修了 `test_timeout_budget.py` 的误报：把**按行正则**改为 `tokenize` 剥掉字符串与注释（docstring 里解释该坑时写的 `timeout=4.0` 被误判成违规）。
- **端到端验证**（真实抓取 215.8s）：`{"status":"partial","new_count":23,"skipped_count":27,"failed_count":3,"total_in_kb":68}`；Qdrant 点数 53 → 68；日志「卡片入库失败」= **0 次**（此前 23 次全部失败）。
- **三条教训**：
  1. **「配置接线成功」不等于「调用成功」** —— 验证要打到调用层；
  2. **失败被 UI 抹平比失败本身更危险** —— 批次表老实记了 `failed`、日志老实记了 23 条失败，但接口回 `status: ok` + 绿色 toast 把两层真话都盖住了。**状态跨层传递时必须保持同一个事实，不能在任何一层被「乐观化」**；
  3. **静态守卫必须用 AST / tokenize，不能用裸正则** —— 正则分不清代码与散文。

### A5. 超时验证方法本身有缺陷（黑洞端口）

- **现象**：任务书 4.3 的验证步骤写「把 `DEEPSEEK_API_KEY` 改成格式合法但无效的值」，**证明不了超时**。
- **根因**：无效 Key 会**立刻返回 401**，根本不会挂起。
- **解决**：改用**黑洞端口**方案 —— 启动一个「只 listen 不 accept」的本地 TCP 端口，让请求真正挂起。
- **附带坑**：必须**持有 `srv.accept()` 的返回值**，否则连接被 GC 立刻关闭。实测：构造期与按次传 `timeout=2` 均在 **2.0s** 抛 `APITimeoutError`。
- **教训**：**验证工具本身也需要被验证**。

### A6. 探针自身踩坑，差点误读为「没有阻塞」

- **现象**：第一版探针在 `create_task(heartbeat)` 之后**立刻**开始计时，对照组一上来就同步阻塞，心跳连一次采样都没做上，`max()` 拿到空序列抛异常。
- **根因**：若只看「改造后没测出阻塞」，很可能把「**探针没工作**」误读成「**没有阻塞**」。
- **解决**：补 `to_thread` 地板值对照（13.2ms），并给探针加呼吸位。
- **教训**：**验证工具本身也需要被验证**（与 A5 同源）。

### A7. 依赖与文档自相矛盾（tenacity / langgraph）

- **现象**：`requirements.txt` 有 `tenacity`、`langgraph`，但**全项目零 import**。
- **根因**：遗留依赖未清理；`resilience.py` 里已写明「不要用 tenacity」，依赖与文档自相矛盾。
- **解决**：移除 `tenacity==8.2.3`（并自研 `resilience.py`）；`langgraph` 属状态机手写未用的遗留。
- **教训**：**依赖清单要定期与实际 import 对账**；写文档时不要把「为什么不用 X」留在代码里却把 X 留在依赖里。

### A8. 韧性三模块的关键设计判断（值得记住）

| 模块 | 关键设计 | 为什么 |
|---|---|---|
| `deadline.py` | `UNBOUNDED = inf`；`clamp_timeout` 预算耗尽**返回 0**（而非小正数） | 统一超时的问题是**各层超时相加会超总预算**（LLM 50s + 重试 + 上游 30s 可到 130s）。deadline 让每层拿到 `min(本层配置, 剩余预算)`，耗尽即降级不发起调用（实测预算 0 → 0.002s） |
| `resilience.py` | `_TIMEOUT_EXC_NAMES` **按类名白名单** | `openai.APITimeoutError` 继承链是 `APIConnectionError → APIError`，**压根不是 `TimeoutError`**，只 isinstance 会漏判 |
| `circuit_breaker.py` | HALF_OPEN 用 `client.set(probe_key,"1",ex=...,nx=True)` **抢单探测** | 否则开放期一到就是**定时惊群**；`_OPEN_KEY_TTL_FACTOR=2` 保证键 TTL 长于开放期 |
| 重试策略 | `max_retries=0` | openai SDK 自带重试会架空我们的超时预算（50s 实际可能 150s），重试必须由应用层统一控制 |
| 熔断口径 | Embedding 的 4xx **既不算成功也不算失败** | 算成功会把失败计数反复清零（攒不到阈值）；算失败则一个错 Key 就能把熔断永久顶在 OPEN |
| 观测 | 超时**单独成事件** `downstream_timeout` | 它指向「预算配得合不合理」，而 `fallback reason=invoke_failed` 指向「下游是不是挂了」，混在一起两类问题都看不清 |

**PG 与验证码明确不重试**：真相源故障不该掩盖 / 安全场景应 fail-closed。

## 4. LLM 与数据质量类（L）

### L1. 摘要字数低估与素材不足幻觉

- **现象**：`qwen-plus` 批量生成 40~90 字摘要时经常**低估字数**（输出 20~38 字）；素材不足时会**编造技术细节**。
- **根因**：模型按 token 估长度、批量输出时更倾向精简；单条诱导扩写反而更易编造与缩水。
- **解决**：**优先批量生成 + 多字段结构化素材**（one_liner / problem / highlights / use_cases / tech_stack）拼接输入；**禁止凭空扩写**；长度未达标程序化复查，仅对不合格项用完整素材重跑。
- **教训**：**宁批量勿逐条诱导**；扩写 prompt 必须显式声明「只基于给定素材、禁止补充素材外细节」。

### L2. 英文卡片漏入知识库（中文化闸门）

- **现象**：英文卡片漏进知识库（实测 65 张中 6 张）。
- **根因**：入库判定只看 `category` 是否存在，不看摘要语言 —— 会放行「摘要失败但残留英文原描述」的卡片。
- **解决**：**三层修复** —— ① prompt 语言要求 → ② `_apply_summary` 单条校验（`is_chinese_text`）→ ③ 入库前 `_summary_applied` **双条件**（`"category" in item` **且** `is_chinese_text(summary)`）。关键：校验失败**不是丢弃结果**，而是摘掉英文原描述 + 清 `category` → 状态回到「未完成」→ 不入库、拿不到去重标记、下次重试（清字段前先落 `raw_description` 保溯源）。
- **附带坑**：`is_chinese_text` 判据是「**汉字数 ≥ 10**」而非占比（占比会被英文术语拉低导致误杀），也不是「非空」。写测试桩时内容要够长，否则 9 个汉字的导读会被**静默丢弃**。
- **教训**：**下游闸门的判据口径要和真实数据分布对齐**（汉字数 vs 占比）。

### L3. FSRS 间隔重复公式错误导致间隔恒为 1 天

- **现象**：复习间隔始终为 1 天，间隔不增长，核心卖点功能失效。
- **根因**：把 `interval` 当 `stability` 回写 —— **stability 与 interval 是两个量纲**，混淆后间隔恒为 1。
- **解决**：区分量纲，间隔公式 `I = S * 9 * (1/R - 1)`。
- **教训**：算法实现里「两个相似量纲混用」是隐蔽 bug 的常见来源，必须有针对性单测。

### L4. 兴趣画像把会话 id 当卡片 id

- **现象**：画像候选里出现 `sess_` 或用户 UUID。
- **根因**：`user_activities.target_id` 是**多变语义列**，含义由 `target_type` 决定 —— 只有 `target_type='card'` 时才是卡片 id；`start_session` / `submit_quiz` 等的 `target_id` 是 `sess_xxx`；`login` / `register` 则是用户 UUID。仅按 `action_type` 过滤会混入脏 id：既取不到向量（白跑 Qdrant），又在 top-N 名额上与真实卡片竞争，还让计数失真。
- **解决**：查询时**同时约束 `target_type == 'card'`**；会话生命周期信号改由 `learning_sessions.card_id` 单独提供。
- **教训**：**多态外键列必须先按类型过滤**再用值；诊断可先 `select target_type, action_type, count(*) group by 1,2` 摸清分布。

### L5. Qdrant 点 ID 类型与 qdrant-client API 变更

- **现象**：upsert 报 `value xxx is not a valid point ID`；`'QdrantClient' object has no attribute 'search'`。
- **根因**：Qdrant point `id` **只接受无符号整数或 UUID**；`qdrant-client` 1.19 **移除了 `search()`**。
- **解决**：用 MD5 把字符串 id 转整数 —— `int(hashlib.md5(key.encode()).hexdigest()[:16], 16)`；改用 `query_points(query=vector, limit=N)`，结果访问 `results.points`。
- **附带坑**：阿里云 DashScope 的 embedding API `text_type` 只接受 `document` / `query`，用 `search_query` 返回 400。

### L8. token 估算粒度不够，导致批量向量化整批 400

> 这是 RAG 块索引（P2）阶段最值钱的一个坑：**只在「真实语料（韩文 README）× 真实协议（批量请求整批失败）」交叉处才出现**，而且我连修两轮都没修对。

- **现象**：全量回填 942 张卡，跑到 914 张时停住。两张卡（`gh-1350986681` 60 块、`gh-1354310030` 28 块）**永远写不进去**，报错只说 `25/60 块向量化失败`，重跑三次都卡在同一处。而真实错误要到 API 原始响应里才看得到：`Range of input length should be [1, 2048]`。
- **根因（估算的粒度本身不够）**：`estimate_tokens` 只区分「中文 / 其他」两类，**韩文被算进「其他」**，按 0.286 token/字符估。实测韩文是 **1.24~1.63 token/字符**，低估 **4~6 倍**。942 篇语料里有 **23 篇含韩文**、21 篇含日文假名、27 篇含西里尔 —— 不是理论风险。
- **为什么代价这么重**：阿里云**批量请求里只要一条超限，整批 25 条一起 400**。所以不是「这一条降级」，而是「**整张卡 60 个块全废**」。而错误信息只报「25/60 失败」，完全指不出根因。
- **两轮都没修对的过程（这段比结论更有用）**：
  1. **第一轮**：改成按文字种类估（韩文 1.40 / 假名 0.95 / 汉字 0.55 / 其他 0.30）→ **仍失败**；
  2. **第二轮**：用 500 字符的**均匀韩文样本**实测，得到 1.24 token/字符，确认 1.40 有富余 → **仍然失败**。真实混排块（1,094 韩文 + 890 拉丁/符号）实测是 **1.63**；
  3. **第三轮**：才想通 —— **token 密度不是文本的固有属性，它依赖上下文**。同一个韩文字在词首、词尾、与拉丁字母相邻时，切分结果都不同。均匀样本测出的密度**只能当参考，测不出上界**。
- **解决**（提交见 RAG P2 阶段）：
  1. 系数改为按文字种类分桶，且**取实测上界再留余量**（韩文 1.75 / 假名 1.10 / 汉字 0.60 / 其他 0.35）；
  2. **不再只靠估算保底** —— 新增 `_batch_aliyun_resilient()`：整批发 → 失败则逐条重发 → 逐条还失败则按 `SHRINK_LADDER`（0.85 / 0.70 / 0.55 / 0.40 / 0.25）截断再发。**把不确定的估算换成确定的验证**；
  3. 用固定档位而非二分：每次验证都要真的发一次付费请求，二分要 11 次、档位最多 5 次；而超长块在真实语料里只占 **0.007%**（13,468 块里 1 块），不值得为它做精确边界搜索。
- **实测**：修正后 942 张卡全部入库，**13,468 块**（与切分器 dry-run 完全一致），退化向量 **0**，触发截断仅 **1 块**，成本约 **¥3.6**。
- **三条教训**：
  1. **估算的「粒度」比「精度」更要紧** —— 我一直在调系数（精度），但真正的问题是分类维度漏了一整类文字（粒度）。**分类错了，系数怎么调都是错的**；
  2. **token 密度依赖上下文，短样本测不出上界** —— 任何「用样本文本测出密度再线性外推」的做法都要留足余量；
  3. **批量协议的失败是「整批连坐」** —— 单条失败被放大成整批失败时，错误信息会完全指不出根因（只报「25/60 失败」）。**对批量接口，必须有「整批失败 → 逐条重试 → 局部降级」的收敛路径**，否则一个局部问题会让整个任务死在同一处。

### L9. 修好的系数被同名的旧表覆盖 —— 兜底机制让它完全不可见

> 这是 L8 的**续集**，也是全项目最隐蔽的一个坑：修完 L8 之后**全量回填成功了**，看起来问题解决了，但实际上**修好的系数从未生效**。

- **现象**：修完 L8 的 token 系数后（韩文 1.40 → 1.75），942 张卡全部入库，13,468 块，看起来完美。几天后做检索模块时顺手核对系数表，发现 `_TOKENS_PER_CHAR` 在 `chunk_spec.py` 里**被赋值了两次** —— 上面是修好的新表（1.75 / 1.10 / 0.60 / 0.35），下面还留着一份旧表（1.40 / 0.95 / 0.55 / 0.30）。**Python 后赋值覆盖前赋值，生效的是旧表。**
- **根因**：编辑时在文件里新增了修正后的表，但**没有删掉原来那一份**。语法完全合法，`import` 不报错，没有任何警告。
- **为什么一直没被发现（两层原因，第二层才是关键）**：
  1. **兜底机制把错误吸收掉了**。L8 里同时加了 `SHRINK_LADDER` 逐级截断重试 —— 就算估算偏低，超限的块也会在重试时被截断后写入。所以**回填照样 100% 成功**，从结果上看不出任何异常。**兜底让配置错误变得不可见**；
  2. **测试的断言方向写反了**。原来的断言是 `assert 1.24 <= per_char <= 1.6` —— 它把**实测上界 1.63 当成了估算的上限**，而正确的要求恰好相反：**估算必须站在实测之上**（估算偏低 → 超限请求真的打到 API）。所以 1.40 这个偏低的系数也能通过。
- **影响（修好之后才看得见）**：
  - 成本估算从 **4,515,341**（旧表）变成 **6,095,236**（新表）。而实际消耗约 **520 万** —— 也就是说旧表**低估 13%**，新表**高估 17%**。
  - 低估的方向是危险的：`--dry-run` 的估算就是用来判断「这个量级要不要跑」的，估低会让你在真正花钱之前放松警惕。
  - 块数与截断数**没有变化**（13,468 块 / 1 块需截断）—— 所以单看运行结果，这个 bug 是**完全不可见**的。
- **解决**：
  1. 删掉陈旧的那一份，并在表上方写明「**本表只能有一份，别在文件别处再写一遍**」；
  2. 加 `test_token_coefficient_table_is_not_shadowed()`：**直接断言生效的系数表**（四个键、四个值、以及 `hangul > kana > cjk > other` 的顺序约束）；
  3. 把原来那条区间断言改成**方向断言**：`assert per_char >= 1.63`（不低于实测上界）。
- **三条教训**：
  1. **有兜底的地方，配置错误不会报错，只会静默地让兜底天天触发**。兜底本身没错，但它会**掩盖它本该暴露的那类问题** —— 所以「加了兜底」之后，必须再单独验证一次「被兜底的那个前提条件本身还成不成立」；
  2. **区间断言会被同方向的错误值骗过去**。当被测对象「必须不低于某个实测界限」时，写成 `lo <= x <= hi` 就给了错误值一半的通过空间。**该写方向就写方向**（`x >= 界限`），别用区间表达方向；
  3. **同一个常量在文件里出现两次，本身就是 bug 的形状**。改配置值时，「新增一份」和「替换原来那份」看起来都像完成了任务，而只有后者是对的。

### L6. Embedding Provider 优先级与维度适配

- **要点**：API Key 优先级为 `ALIYUN > VOYAGE > ZHIPU > Mock`，**不要用 `DEEPSEEK_API_KEY` 作 Embedding 源**；需**动态向量维度检测**（`vector_dim = len(vector)`），因不同 Provider 维度不同（阿里云 1024 / OpenAI 1536）；Qdrant 连接失败先查容器是否启动。

### L7. LLM-as-judge 评测门禁的要点

- **要点**：
  1. 裁判 temperature **必须为 0**，否则同一输出每次打分漂移，噪声掩盖真实退化；
  2. 裁判的「事实边界素材」与「格式规则」必须与生成 prompt 的输入/约束**逐一对应**（少给字段会误判编造，生成放宽约束而裁判未同步会系统性扣分）；
  3. **相对回归线容差 ≈ 连跑 3 次实测各维度 σ 的 2 倍**；绝对硬线须相对实测均值留 ≥2σ 余量，否则必然假红；
  4. 门禁跑**全量样本**（<6 条时单条波动就能让均分跳 0.2+）。
- **教训**：性质维度（语言正确性、无编造）用绝对硬线兜底，其余维度用相对回归线；刻意写坏的标定样本单独汇总、**不计入基准均分**。

### L10. 检索评测的两个口径陷阱（排序 vs 拒答 / 包含 vs 重叠）

- **背景**：给块索引建标注评测集时（46 条：36 正 + 10 负），差点因为两个口径错误得出反向结论。
- **要点**：
  1. **排序指标与拒答指标必须分两次跑**。算 `hit@k` 时 **`min_score=0.0`（不过阈值）**，算拒答时**才用真实阈值**。混在一起跑会得到一个假象：阈值调高 → 命中率下降 → 看起来「检索变差了」。其实降低的是「通过阈值的召回数」，不是「召回本身」。**同一套标签、两个口径、分开报**，否则「库里没有」和「召回了但不够像」会被压成同一个观测值。
  2. **命中判定用「严格包含」而不是「重叠」**。`hit.char_start <= span[0] and hit.char_end >= span[1]`（块完整包住答案）。重叠口径会把「答案横跨两个块、每块各一半」也算命中，但此时模型拿到的信息是不完整的 —— 命中率会虚高。
  3. **标签锚在「原文字符区间」而不是「块编号」**。块编号随切分参数（`size` / `overlap`）变，字符区间不变。锚在字符区间上，重切之后只需重算「区间落在哪个块里」，**同一套 46 条能跨策略复用** —— 这正是能做「按标题切 vs 固定长度」对比的前提。
  4. **出题前先做物理可达性自检**：答案区间必须能被**某个已入库的块完整包含**。否则这条题**物理上不可能命中**，会人为压低命中率、把评测集变成「测切分器缺陷」而不是「测检索」。
  5. **必须把「召回层」和「排序层」拆开看**。`hit@k` 把两件事混在一起：答案**有没有被召回到**（前 10 里有没有）和**召回后排在几名**。拆开才发现：按标题切 vs 固定长度的**召回层完全打平（都是 32/36）**，差异**全在排序**。不拆开就会得出「该换切分器」的错误结论 —— 而正确结论是「该上重排」。
  6. **聚合指标赢 ≠ 统计显著**。按标题切在 5 个聚合指标上 4 胜 1 平（hit@1 +13.9pt、MRR +0.083），但 n=36 的**配对符号检验 p=0.55、配对 t 检验 t=−1.14**，都到不了显著。**「看起来赢了」和「证明了赢」是两件事** —— 前者只能作为方向性证据，要定论得扩样本（100+ 条）。
- **教训**：
  - 自己出题（读过原文再问）得到的是**乐观上界**，因为用词会不自觉贴近原文。**报数时必须主动补这句**，并说明它只用于**策略间相对比较**（同一套标签、同一套口径，出题偏好被抵消）。
  - **「数字能复现」比「数字好看」重要**。最早那组检索相似度是临时代码跑出来的、复现不了；固化成一个脚本（`retrieval_runner.py`）之后，评审时说「你跑一下」就能当场重算 —— **可信度来自可复现，不来自数值高低**。
  - **宁可宣布自己的门禁没通过，也不要挑一个好看的口径宣布通过**。前者证明你懂统计，后者一问就穿。

## 5. 前端类（F）

### F1. 全屏遮罩浮层跨路由被无差别展开

- **现象**：进入某页面就被一层全屏半透明遮罩压住，tab / 按钮全点不动，但 DOM 结构看起来正常。
- **根因**：浮层的「打开」状态存在**全局 store 里、跨路由保持**，而浮层组件内部又有「挂载时自动恢复内容并展开自己」的副作用。二者叠加，只要组件被挂在该路由上，用户一进来就会看到它自己展开。本例中学习抽屉被无条件挂在「我的」页，挂载时恢复上次未完成会话并 `setOpen(true)`。
- **解决**：让浮层在**不需要它的路由上延迟挂载**（用户主动触发时才渲染），而不是先挂载再纠正打开状态。
- **教训**：**全局单例状态的浮层组件，「打开」语义与挂载点强耦合**，必须显式设计「哪个路由该挂、挂上是否自动展开」。

### F2. 学习抽屉单向状态机无法回退

- **现象**：卡片点「开始学习」再点「卡片要点」后，**回不去看 README 的节点**。
- **根因**：learning store 的五态状态机 `idle/loading/reading/explanation/chatting` **是单向的**：`reading → explanation → chatting` 之后没有任何回退路径。更严重的是在问答态想对照原文只能关抽屉，而关掉会丢掉 `sessionId` 与全部 `messages`。
- **解决**（提交 `ee5589d`）：新增 `backToReading`，**只 `setState('reading')`**，刻意不动 `sessionId`/`messages`/`content`/`digest`/`readView`。设计判断：**回退一个视图不该清掉用户已付出的会话成本**；这也是它与 `startLearning`（开始新学习、重置全部状态）的本质区别。
- **验证**：真实 Chrome 探针 16/16 全绿；**截图逐字节比对** —— 往返后截图字节数相等 ⇒ 零状态丢失（这是个便宜且灵敏的回归信号）。
- **教训**：状态机设计要先问「有没有回退语义」，别让用户的会话成本被视图切换清掉。

### F3. Alpine.js 变量名拼写错误

- **现象**：控制台报 `Alpine Expression Error: currentExplanatio is not defined`。
- **根因**：`currentExplanatio` 少了个 `n`（应为 `currentExplanation`）。
- **解决**：改正拼写（旧版 `frontend/index.html`，现已重构为 React）。

## 6. 安全与人机校验类（S）

### S1. VAPTCHA V4 沿用 V3 契约导致全链路失败

- **现象**：前端控件加载失败、后端全部返回 400。
- **根因**：V4 与 V3 契约完全不同，且旧域名已下线。四处必错点：
  1. 前端 SDK 地址应为 `https://c4.vaptcha.com/src/v4.js`（旧 `api/cdn.vaptcha.com` 已 NXDOMAIN）；
  2. 服务端校验端点为 `POST https://v41.vaptcha.com/api/verify`；
  3. 请求体是 **JSON**，密钥字段名为 **`vkey`**（非 `secretkey`、非 form）；
  4. 返回需读 `data.result === true` **且** `data.code === 0`（0 通过 / 1 鉴权不通过 / 2 token 过期 / 3 其它失败）。
- **解决**：以**官方文档 + 真实端点实测 + 浏览器 SDK 探针**三者交叉确认，不靠猜。
- **教训**：升级第三方服务时，**契约（域名 / 端点 / 字段名 / 返回结构）必须逐项对齐**。

### S2. VAPTCHA 验签失败：`ip` 是签名字段

- **现象**：后端调用官方校验返回失败（`code != 0` 或 `result != true`），但 token/knock/dfu 看起来都对。
- **根因**：V4 签名公式为 `HMAC-SHA256(timestamp + "." + ip + "." + dfu + "." + knock, vkey)` —— **`ip` 是被签名覆盖的字段**。本机开发时前端 `validate()` 返回的是**公网 IP**，而后端拿到的是 `127.0.0.1`，不一致必然验签失败。
- **解决**：前端把 `validate()` 返回的 `ip` 一并回传（字段 `captcha_ip`）；后端优先用它，`remote_ip` 仅作兜底。这不会造成越权 —— 改 `ip` 只会让验签失败，无法伪造通过。
- **教训**：**凡「token + 伴随签名字段」的风控服务，伴随字段必须原样回传，缺一即失败**。

### S3. passlib + bcrypt 版本不兼容

- **现象**：密码哈希相关代码崩溃。
- **根因**：bcrypt 4.1+ 删了 `bcrypt.__about__`，passlib 1.7.4 会崩。
- **解决**：**必须钉 `bcrypt==4.0.1`**。
- **教训**：密码学 / 底层库的**间接依赖要钉版本**。

### S4. 项目不需要短信功能（避免无谓配置）

- **结论**：注册登录仅用 VAPTCHA 挡批量注册，不做邮箱/短信验证码；找回密码走邮件链接；`users` 表只有 `email/username`，无 `phone` 字段。代码里的 `mobile` 只是技术分类标签。**VAPTCHA 短信是计费的，暂不开可节省费用**。

## 7. 工程方法与流程类（G / 元教训）

### G1. 事故：工作区 43 个文件被清空

- **现象**：执行 `git rm` 删除两个文件的命令返回 SIGTERM 且无输出。随后 `backend/src/` 下 `models/`、`modules/`、`schemas/`、`services/`（共 43 个文件）整个消失，只剩 `api/` 和 `core/`。
- **根因**：`.git/index.lock`（0 字节，与命令被中断同一时刻）残留 → git 处于「另一个进程持有锁」状态；**命令被强杀时索引写入被中断，工作区被半途应用**。
- **恢复步骤**（已验证）：
  ```bash
  # 1. 先确认没有真的 git 进程在跑（避免误删正在使用的锁）
  ps -W | grep -i git          # 只有自己的 bash，无 git.exe
  ls -la .git/index.lock       # 0 字节 + 时间戳＝被中断的时刻 ⇒ 过期锁
  # 2. 移除过期锁
  rm -f .git/index.lock
  # 3. 从 HEAD 恢复（只影响已跟踪文件，不动未跟踪内容）
  git checkout -- backend/src
  # 4. 用「限定路径」的 status 验证
  git status --short -- backend/src     # 输出为空 ⇒ 已一致
  ```
- **教训（已沉淀为技能 `agent-safe-repo-refactor`）**：
  1. **不要用 `git rm` 同时改工作区与索引** —— 拆成 `rm 文件` → 验证 → `git add -A <路径>`；
  2. **命令被 SIGTERM 后，下一步 git 操作前先查 `.git/index.lock`**；
  3. **`git status` 一律限定路径**（本仓库有 `backend/ilo/` 的 1695 个 pyc 与 `frontend/node_modules`，全仓 status 多次卡到 SIGTERM）；
  4. **任何破坏性操作后立刻用限定路径 status 验证**，不要连做几步再检查；
  5. 受版本控制的文件丢了不可怕 —— 先 `git ls-files <path>` 确认索引完好，再 `git checkout -- <path>`。

### G2. 「摘要会过期」——写文档前必须重新核验

- **现象**：基于对话摘要里的旧结论把「唯一未修缺口」写进 3 份文档，实际该问题**早已修完**（提交 `9d0f033` 在写文档之前）。
- **根因**：**摘要是会过期的**。基于旧结论写文档，且未重新核验代码。
- **解决**：任何要写进文档的事实，**交付前必须对代码重新核一遍**；任务书被执行后，回头 grep `仍未修|唯一未修|已知缺口` 并逐条核验。
- **教训**：**用户拿一个已修的缺口去对外陈述，等于承认不了解自己的代码库。**

### G3. 误报比漏报致命（守卫必须用 AST）

- **问题**：静态守卫若用裸正则/按行匹配，会犯两类错：误判（`await kb.upsert()` 被当同步）和漏判（换变量名就搜不到）。
- **解决**：用 **AST 分析**。分析器做三件正则做不到的事：
  1. 排除 `await` 的调用和 `gather` 的实参；
  2. **资源污染跟踪** —— 但**只有 IO 工厂才传播**：`find_cards()` 做 IO 但返回**数据**，`cards.get()` 只是查字典。不区分「资源」和「数据」会全误报；`random.sample` 是纯计算，不能进黑名单；
  3. **本地同步函数传染** —— `_personalized_items()` 这种「同步 def、内部做 IO、被 async 路由直接调」的最易漏。
- **教训**：**误报比漏报致命 —— 它会让守卫被当成噪声然后被关掉。** 守卫还必须有「牙齿」（12 例里 8 例是守卫自检），且黑名单完整性要被测试锁住（实测被 `count_activities` / `list_messages` **漏项两次**打脸，故加了反查路由实际调用函数的交叉检查）。

### G4. 文档真实性 / 去求职化规范

- **规范**：公开文档（README）**移除求职/面试相关表述**（如「面试级」「求职项目」），并修正因文件迁移导致的失效引用；用「示例数据 / 降级」等**中性真实表述**替代生硬的 "Mock" 措辞，**不夸大功能**。

### G5. 惯性提交策略：「长任务同步返回」是架构取舍而非 bug

- **遗留**：`/discover/refresh` 与 `/refresh-articles` 仍是**单请求内跑完整条抓取 + 摘要链**（可能几分钟）。Phase 5 只保证它**不阻塞事件循环**，**没做异步队列化**。
- **性质区分**：这与「不该阻塞却阻塞了」（bug）不同，这是「长任务同步返回」（**架构取舍**）。要真正解决得上任务队列 —— 接口返回 `task_id`，前端轮询或 SSE。
- **教训**：**诚实边界要主动说，且要说清「这是取舍不是遗漏」**。

## 9. 一句话教训精选（可当 checklist）

1. **报错现象 ≠ 真实原因** —— Windows 上 `localhost`→IPv6、healthcheck 缺 curl、中文路径当模块名，都是「现象指东，原因在西」。
2. **失败被 UI 抹平比失败本身更危险** —— 状态跨层传递时必须保持同一个事实，不能在任何一层被「乐观化」。
3. **「配置接线成功」不等于「调用成功」** —— 验证要打到实际执行路径。
4. **搜索维度错了，就一定会漏** —— 别按技术栈搜，要按「`async def` 里出现了哪些同步 IO」搜。
5. **带 baseline 的守卫等于没有守卫** —— 误报比漏报致命，守卫必须用 AST 且有自检。
6. **验证工具本身也需要被验证** —— 探针没工作会被误读为「没有阻塞」。
7. **摘要是会过期的** —— 写进文档的事实，交付前必须对代码重新核一遍。
8. **回退一个视图，不该清掉用户已付出的会话成本** —— 状态机要设计回退语义。
9. **「修 A 引入 B」的代价要当场盘点** —— 改 async 修复一处，要以不引入新阻塞为前提。
10. **诚实边界主动说，并说清「取舍 vs 遗漏」** —— 评审与协作都吃这一套。
11. **估算的「粒度」比「精度」更要紧** —— 分类维度漏了一整类（韩文被当成「其他」），系数怎么调都是错的。
12. **批量协议要设计「整批失败 → 逐条重试 → 局部降级」的收敛路径** —— 单条失败被放大成整批失败时，报错会完全指不出根因（只报「25/60 失败」）。
13. **实测密度不能线性外推** —— token 密度依赖上下文，均匀短样本测不出上界；要么留足余量，要么用真实调用验证。
14. **有兜底的地方，配置错误不会报错，只会静默地让兜底天天触发** —— 加了兜底之后，必须再单独验证一次「被兜底的那个前提条件本身还成不成立」（L9：系数表被覆盖，回填照样 100% 成功）。
15. **区间断言会被同方向的错误值骗过去** —— 当被测对象「必须不低于某个界限」时，写成 `lo <= x <= hi` 就给了错误值一半的通过空间；**该写方向就写方向**。
16. **同一个常量在文件里出现两次，本身就是 bug 的形状** —— 改配置值时，「新增一份」和「替换原来那份」看起来都像完成了任务，只有后者是对的。
17. **「跑通了」不等于「配置生效了」** —— 凡是「有兜底、有重试、有降级」的链路，成功的结果都不能证明上游参数是对的。要验证参数，得直接断言参数本身。
18. **一个指标混两种口径，就会得出反向结论** —— 算排序（hit@k）和算拒答必须分开跑；混在一起会看到「阈值调高 → 命中率下降」的假象，实际变的是「通过阈值的数」，不是「召回本身」。
19. **命中判定要严于直觉** —— 「严格包含」而非「重叠」：答案是块的子串才算命中，否则「答案横跨两块各一半」也算中，命中率虚高而模型信息不全。
20. **标签锚在「不随参数变的东西」上** —— 锚原文字符区间，不锚块编号。这是「同一套评测集能跨切分策略复用」的前提，也是能横向对比两种切法的唯一办法。
21. **可复现比好看重要** —— 临时代码跑出的数字等于没有数字；固化成一个能当场重跑的脚本，可信度来自「能重算」，不来自数值高低。
22. **一个指标混两层，就会得出错误的下一步** —— `hit@k` 同时含「召回到了没」和「排得靠前没」。拆开才知道两套切法**召回层打平、差异全在排序** → 该上重排，不是换切分器。
23. **聚合赢 ≠ 显著** —— 5 项里赢 4 项看着很稳，但 n=36 时配对检验 p=0.55。**「看起来赢了」只能算方向性证据**；要定论就扩样本，别把「好看」当成「证明」。
